# General taste
- When a feature is requested, prefers the full, complete surface ("implement this properly") over the smallest useful increment. Confidence: 0.6
- Prefers keeping niche/backends/forge support rather than dropping it to go deeper on the two most popular ones. Confidence: 0.6
- Open to being told what is out of scope, as long as the core ask is delivered in full. Confidence: 0.5
- For large or greenfield builds, expects a written design plan first — architecture decisions, file list, tests, out-of-scope, known cleanup — reviewed before code is written. Confidence: 0.65
- Values plans that explain the crux mechanism concretely (e.g. a `FetchSpec` / per-backend refspec table) rather than a feature bullet list. Confidence: 0.6
- Sends terse, lowercase, fragment prompts ("implement this properly …") and expects intent to be inferred and the job done end-to-end rather than being asked a string of clarifying questions. Confidence: 0.65
- Appreciates proactively surfacing naming/documentation drift and stale duplication in the codebase as part of a plan, instead of silently inheriting it. Confidence: 0.55
- Approves plans tersely ("all approved") and expects work to start immediately without further ceremony; when approval is ambiguous the right move is one crisp clarifying question, then proceed. Confidence: 0.55
- Builds in large multi-step increments: keep a visible todo list, and re-sync it as items complete or scope is added mid-flight, so the user can see progress without asking. Confidence: 0.5
- Prefers honest degradation over fabricated capability: when a backend genuinely cannot do something (no merge API, no draft concept, no PR ref namespace), return an explicit "not supported" error explaining the real constraint rather than inventing a plausible-looking implementation. Confidence: 0.6
